정해진 다섯 시각에 AI가 먼저 안부를 묻고, 답변을 분석해 꼬리질문을 이어 갑니다. 답변 여덟 번이면 한 세션이 끝납니다. 음성은 텍스트로 바꿔 분석하고 표정은 말풍선이 오가는 동안에만 읽으며, 질병을 판단하지 않고 평소와 달라진 지점만 보호자에게 전달합니다.

09:00 아침 식사는 하셨어요? 12:00 점심은 맛있게 드셨어요? 15:00 오늘 기분이 어떠세요? 18:00 요즘 즐거운 일이 있나요? 21:00 오늘 하루는 어떠셨어요?

02

세 파트의 경계

무엇을 하는지보다 무엇을 하지 않는지가 경계를 정합니다. 아래 금지 항목을 지키면 한쪽을 고쳐도 다른 쪽이 깨지지 않습니다.

Frontend

Next.js · 이윤아
  • 말풍선 대화 화면과 결과 화면
  • 마이크 녹음, 종료 시점 판정
  • 말풍선 구간에만 카메라 프레임 수집 (2초 간격, 최대 5장)
  • 오디오와 프레임을 한 요청으로 묶어 업로드
  • AI 응답 텍스트를 음성으로 재생
하지 않는 것
  • 표정 분류 (모델은 서버에만)
  • 감정 판정
  • AI 서버 API 키 보유
  • 음성·프레임 원본 보관

Main Backend

Spring Boot · 남궁명진
  • 다섯 시각 스케줄러, 고정 질문 전달
  • 세션 생성·종료 판정, 진행 상태 보관
  • AI 서버 호출 중계 (키는 여기만 보유)
  • 턴 결과 저장, 시간대 최빈값 집계
  • 보호자 알림 발송, 일일 요약 생성
하지 않는 것
  • 모델 실행
  • 프롬프트 작성·관리
  • 말과 표정을 합치는 판단

AI Server

FastAPI · 이재희
  • STT, 표정 분류, 정서 신호 추출
  • 말벗 응답과 꼬리질문 생성
  • 말 + 표정을 합쳐 턴 결과 1개 산출
  • 개인 기준선 비교 판정
  • 프롬프트 버전 관리, 개선용 로그 적재
하지 않는 것
  • 사용자 관리·인증
  • 알림 발송
  • 세션 상태 보관 (무상태 유지)
  • 서비스 원본 데이터 소유
AI 서버는 무상태로 둡니다.

턴 하나를 받아 결과 하나를 돌려줄 뿐, 그 세션이 몇 번째 턴인지 몇 초가 지났는지는 기억하지 않습니다. 세션 상태는 Backend가 Redis로 들고 있습니다. 이렇게 두면 AI 서버를 재시작하거나 여러 대로 늘려도 대화가 끊기지 않고, 턴 수·제한 시간 규칙이 바뀌어도 AI 코드는 그대로입니다.

03

전체 흐름 네 단계

보호자가 손댈 것은 없고, 정해진 시각에 자동으로 시작합니다.

BE 스케줄러

① 시간대 도래

09·12·15·18·21시에 그 시각의 고정 질문을 피보호자 앱에 띄웁니다. 문구는 DB에 다섯 건으로 들어 있습니다.

피보호자 · AI

② 대화 세션

“답하기”를 누르면 시작합니다. 고정 질문 1회에 꼬리질문 7회를 더해 답변 8번이면 종료합니다. 질문 하나의 대화는 시간 제한 없이 답변 8번이면 종료합니다(사용자 결정, 2026-10-29). 백엔드와 협의해 명세 Q11을 개정했습니다(2026-11-01).

BE

③ 세션 집계

턴 결과를 세어 최빈값을 그 시간대의 결과로 삼습니다. 화면에는 이 한 값만 보여 줍니다.

BE + AI

④ 일일 요약

21시 세션이 끝나면 다섯 시간대를 모아 AI에 기준선 비교를 요청하고, 달라진 점만 보호자에게 보냅니다.

04

데이터 흐름도

턴 한 번이 도는 동안 누가 누구에게 무엇을 보내는지입니다. 세로선은 각 파트의 시간축입니다.

AI 서버를 부르는 쪽은 언제나 Backend입니다. Frontend는 AI 서버 주소도 키도 모릅니다. ⑦번 적재는 응답을 막지 않도록 비동기로 돌려, 로그 저장이 실패해도 대화는 이어집니다.

05

AI가 Backend에 넘기는 정보

엔드포인트는 두 개면 충분합니다. 기존 SilverBridgeAiServer의 규칙을 그대로 따릅니다. 경로는 /api/v1/…, 인증은 X-API-Key, 응답은 success_response(message, data) 래핑, 필드명은 camelCase입니다.

턴 결과 라벨(turnResult, 시간대 집계)은 기쁨·평온·슬픔·화남·우울 5개와 판단 보류로 씁니다 (CH-052, CH-057). 말과 표정이 반대 방향이면 CONFLICT로 보고 판단 보류를 씁니다. 텍스트 감정 6개(GGARA02)와 표정 8개(HSEmotion)는 제안 매핑으로 5개에 대응시켰습니다 (CH-057).

DB를 둘로 나눕니다

서비스가 쓰는 데이터와 AI 개선에 쓰는 데이터는 목적이 다릅니다. 같은 테이블에 두면 한쪽 요구가 다른 쪽을 망가뜨립니다.

서비스 DB · Backend 소유

보호자 화면, 알림, 요약이 전부 여기서 나옵니다. 데이터의 원본은 언제나 이쪽입니다.

테이블담는 것
question_template고정 질문 5건 - 시간대, 문장, 사용 여부
conversation_session세션 1건 - 시간대, 시작·종료, 완료 턴 수, 종료 사유(COMPLETED/USER_STOP/NO_RESPONSE/ERROR), 시간대 결과
conversation_turn턴 1건 - 질문 id, transcript, 신호 7개, 표정 라벨, 결합 결과, promptVersion
daily_emotion_summary하루 1건 - 시간대별 결과, 무응답 수, 기준선 판정
emotion_baseline개인 기준선 - 평소 신호 분포, 평균 발화 길이, 갱신 시각

AI 개선 DB · AI 서버 소유

서비스는 이 DB를 읽지 않습니다. 여기가 고장 나도 대화와 알림은 그대로 돕니다.

테이블담는 것
utterance_log비식별 id, 질문 id, transcript, 신호 7개, 표정 라벨, 결합 결과, promptVersion, 처리 시간
eval_set사람이 정답을 붙인 평가용 발화. 프롬프트를 바꿀 때 전후 비교에 씀
prompt_version프롬프트 전문, 적용 기간, 변경 사유
개인 식별자를 그대로 넣지 않습니다.

개선 DB에는 서비스의 memberId 대신 되돌릴 수 없는 해시를 씁니다. 이름·전화번호·주소는 아예 보내지 않고, 발화 안에 사람 이름이나 지명이 섞여 들어오는 경우까지 생각하면 적재 전에 한 번 걸러야 합니다. 같은 사람의 발화를 묶어 볼 수는 있되, 그 사람이 누구인지는 이 DB만으로 알 수 없어야 합니다.

11

모은 대화를 어디에 쓸 것인가

쌓인 발화로 모델을 더 학습시키는 것과, 프롬프트와 임계값을 다듬는 것은 비용도 효과도 전혀 다릅니다.

용도필요한 것현실성
프롬프트 v2 개선
실제 발화 패턴을 보고 판단 기준과 예시를 보강		 발화 수백 건 지금 가능
잠정 임계값 확정
응답 길이 분포, unknown 비율, 기준선 폭		 한 사람당 2~4주 누적 지금 가능
평가셋 구축
프롬프트를 바꿀 때 좋아졌는지 나빠졌는지 비교		 사람이 정답을 붙인 100~300건 지금 가능
감정 분류 모델 별도 학습

AI가 뽑은 신호를 그대로 정답 삼아 학습하면 오류가 굳습니다.

예를 들어 지금 프롬프트는 “내일 경로당 가려고”를 socialContact: mentioned로 잘못 판정합니다. 이 결과를 라벨로 써서 학습시키면 그 오류가 모델에 박혀 더 고치기 어려워집니다. 편향 강의의 피드백 루프가 정확히 이 모양입니다. 학습에 쓰려면 사람이 다시 정답을 붙인 데이터여야 합니다.

서비스 제공과 AI 학습은 별개의 목적입니다.

“안부를 묻고 보호자에게 알린다”에 동의받은 데이터를 모델 학습에 쓰려면 그 목적으로 따로 동의를 받아야 합니다. 독거노인의 발화는 생활·건강·관계가 다 드러나는 민감한 내용이고, 피보호자 본인이 동의 절차를 이해하기 어려운 경우도 많습니다. 동의 항목을 분리하고, 거부해도 서비스는 그대로 쓸 수 있어야 합니다.

권하는 순서. 먼저 utterance_log에 쌓기만 합니다. 수백 건이 모이면 직접 읽어 보면서 프롬프트 v2를 만들고, 잠정값으로 둔 임계값을 실제 분포에 맞춥니다. 그 과정에서 애매했던 발화를 골라 사람이 정답을 붙이면 그게 eval_set이 됩니다. 별도 모델 학습은 평가셋이 생긴 다음에 판단해도 늦지 않습니다. 순서를 바꾸면 좋아졌는지 나빠졌는지 잴 방법이 없습니다.

지금 정해야 할 것

  1. 팀장 서버에서 EXAONE을 어떻게 돌릴 것인가AI 서버에 Ollama가 없어서 transformers로 직접 로드하기로 정했습니다 (CH-052). 그래도, MedGemma가 이미 올라가 있어 VRAM 여유를 확인해야 합니다.
  2. 팀장 STT와 TTS 모델한국어 정확도, 노인 발화 처리, 속도, 라이선스 기준으로 선정. 이 둘이 정해져야 턴 시간 예산이 완성됩니다.
  3. 팀 전체 중도 이탈과 조기 종료 기준8턴 고정과 시간 제한 없음(사용자 결정)이 정해졌습니다. 턴 시간 예산은 체감 기준으로 따로 확인합니다. 대신 끝까지 못 간 세션을 집계에 넣을 기준(잠정 3턴)과 연속 무응답 시 조기 종료 기준(잠정 2회)을 정해야 합니다.
  4. 팀 전체 라벨 대응표브로슈어는 평온·기쁨, EXAONE 신호는 positive·neutral·negative, HSEmotion은 또 다른 체계입니다. 세 가지 대응표가 없으면 “표정 최빈값 채택” 규칙이 코드가 되지 않습니다.
  5. 백엔드 세션 상태를 Redis로 둘 것인가AI 서버를 무상태로 두려면 턴 수·경과 시간을 Backend가 관리해야 합니다.
  6. 프론트 프레임 수집 간격과 해상도2초 간격, 얼굴 영역 위주의 작은 이미지를 가정했습니다. 카메라 권한, 업로드 용량, 배터리를 함께 봐야 합니다.
  7. 팀 전체 학습용 수집 동의개선 DB 적재를 서비스 동의와 분리할지, 그렇다면 동의 화면을 누가 만들지. 동의 없이 쌓기 시작하면 나중에 지워야 합니다.

                    대답이 짧아졌습니다. 대화를 끝까지 이어가는 날도 줄었습니다.",
    "promptVersion": "v1"
  }
}
보호자에게 보여줄 문장은 AI가 씁니다.

summaryText를 Backend가 숫자로 조립하지 않고 AI가 완성해서 넘깁니다. 질병명을 쓰지 않는다는 규칙을 한 곳에서만 지키면 되기 때문입니다. Backend가 “부정 비율 38%” 같은 숫자를 직접 문장으로 만들기 시작하면 표현 규칙이 두 군데로 흩어지고, 나중에 누군가 “우울 경향” 같은 단어를 넣게 됩니다. URGENT는 여기서 나오지 않습니다. 위험은 턴 단위에서만 판정합니다.

D. AI가 보장하는 것

무상태세션이 몇 번째 턴인지, 몇 초 지났는지 기억하지 않습니다. 재시작하거나 여러 대로 늘려도 대화가 끊기지 않습니다.
대화 우선STT 실패, 얼굴 미검출, 신호 추출 실패는 모두 200으로 돌려주고 reply는 정상 생성합니다. LLM이 실패해도 503을 내지 않고 미리 정한 대체 문장으로 대화를 이어 갑니다 (CH-057, D20).
원본 폐기오디오와 프레임은 분석 직후 버립니다. 디스크에 남기지 않습니다.
질병명 금지응답의 어떤 문자열에도 우울증·치매·불안증 등을 넣지 않습니다.
버전 표기모든 응답에 promptVersion을 붙입니다. 판정 기준이 바뀌면 버전이 올라갑니다.

E. Backend가 책임지는 것

세션 상태턴 번호 증가, 8턴 도달 판정, isLastTurn 세팅, 종료 사유 기록.
집계turnResult.emotionLabel의 최빈값으로 시간대 결과 산출. 동점이면 더 부정적인 쪽.
알림risk:true 즉시 발송, 변화 알림(alertLevel NOTICE)은 세션 종료 시 즉시, 일일 요약은 alertLevel에 따라 발송 (사용자 결정 2026-11-01).
원본 보관질문·세션·턴·요약·기준선의 원본은 서비스 DB에만 둡니다.
키 보유X-API-Key는 Backend만 가집니다. Frontend에 내려보내지 않습니다.
집계 제외 판단signals:null인 턴, ERROR로 끝난 세션, 3턴 미만 중단 세션을 집계에서 뺍니다.

F. 서로 하지 않기로 한 것

Frontend표정 분류, 감정 판정, API 키 보유, 음성·프레임 보관
Backend모델 실행, 프롬프트 작성, 말과 표정을 합치는 판단, 보호자용 문장 조립
AI사용자 관리·인증, 알림 발송, 세션 상태 보관, 서비스 DB 접근
