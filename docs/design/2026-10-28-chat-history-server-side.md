## 1. 문제

`POST /api/v1/chat`의 `history`는 클라이언트가 보낸다. FE는 화면에 보이는 말풍선 최근 24개를 그대로 싣고, BE 중계(`ChatRelayService`)는 개수(24)만 막고 그대로 넘긴다. AI는 이 값을 서버 기록과 대조하지 않는다. 그래서 요청 본문을 고친 사람이 "assistant" 발화나 지난 사용자 발화를 지어내 넣을 수 있다.

**막고 싶은 것**: 지어낸 이력으로 라우팅·예약 상태·안전 판단이 바뀌는 것.
**막을 필요가 없는 것**: 자기 계정으로 자기 상담을 망치는 것 자체(공격자가 얻는 것이 없다). 위험한 경우는 "위기 응답을 피하는 것"과 "예약 값이 엉뚱하게 들어가는 것" 두 가지다.

## 2. history를 쓰는 곳 (현재)

| # | 쓰는 곳 | 하는 일 | 조작 시 영향 | 서버 기록으로 대체 |
|---|---|---|---|---|
| H1 | 라우터 프롬프트 `ChatRouterService.route` | 최근 8턴 + 그 이전 요약 500자 → 경로·응급·자해 판단 | 지어낸 assistant 발화("예약 진행 중")로 경로를 예약으로 끌거나, 위기 맥락을 지워 `self_harm` 판단을 흐릴 수 있다 | 가능 - 같은 사용자·세션의 `chat_logs.message`·`reply` |
| H2 | 예약 추출 프롬프트 | 처음부터 만드는 턴에서 진료과·날짜 등 추출 | 이력 속 값이 초안으로 들어간다(확인 카드 단계에서 사용자가 보게 된다) | 가능. R-8 이후 이어 쓰는 턴은 이미 서버 초안만 본다 |

| H6 | `_crisis_continues_without_router` | 라우터 실패 시 짧은 말을 위기 지속으로 본다 | H5와 같음 | 가능 |
| H7 | 위기 해제 판단 `_previous_turn_meta` | 직전 턴 selfHarm·crisisFollowup | **이미 서버 기록**을 쓴다 | - |
| H8 | `_department_question_reply` | "무슨 과?"에 직전 assistant 답의 진료과 | 지어낸 assistant 발화로 엉뚱한 과 안내 | 가능 - 직전 `reply` |
| H9 | `_fallback_reply` 문맥 힌트 | 직전 사용자 발화 앞 30자를 답에 되돌려 씀 | 지어낸 문장이 답에 그대로 보인다(자기 화면이라 피해는 작다) | 가능 |

## 3. 서버 기록에 이미 있는 것

`chat_logs` 행 = 한 턴. `user_id`, `message`(사용자 원문, 버튼 턴은 `[선택] field: value`), `reply`, `context_json.sessionId`, `upstreamMeta`(`router.route`·`router.wardId`·`selfHarm`·`crisisFollowup`·`flowState`·`pendingAction`). 같은 `user_id`·`sessionId`로 시간순 조회하면 이력을 다시 만들 수 있다. `created_at` 인덱스는 #87에서 생겼다. `(user_id, id)` 조회는 지금도 직전 1건 조회에 쓰고 있다.

FE와 다른 점:
- 버튼 턴: FE는 버튼 **라벨**("강남메디내과")을 사용자 말로 싣고, 서버 기록은 `[선택] hospital: 강남메디내과`다. 라우터·추출이 보는 글이 달라진다.
- 시작 인사(`welcome`)는 FE도 빼고 서버에도 없다.
- 위기 고정 응답·109 한 줄은 서버 `reply`에 그대로 있다.
- FE 새로고침·다른 기기: FE 이력은 비고, 서버 기록은 같은 세션이면 남는다(세션 ID는 FE가 정한다).
- 보호자의 대리 상담: 기록은 보호자 `user_id`로 남고 `router.wardId`로 피보호자가 구분된다. 이력을 다시 만들 때 **같은 wardId의 턴만** 써야 한다(다른 피보호자 상담이 섞이면 안 된다 - 라우터 상태 기억과 같은 규칙).

## 4. 방안

### A안 (추천) - 서버 이력만 쓰고 클라이언트 history는 무시한다
1. `ChatService`가 요청 처음에 `chat_logs`에서 같은 `user_id`·`sessionId`·`wardId`의 최근 N턴(사용자·assistant 쌍, 기본 12개)을 읽어 `history`를 만든다. 버튼 턴은 `[선택] …` 대신 선택값만 쓰거나 생략한다(아래 결정 3).
2. 요청의 `history`는 읽지 않는다(스키마는 하위 호환으로 남긴다 - BE·FE 계약 변경 없음).
3. 위기 근거(H5·H6)는 서버 기록의 `selfHarm` 표시까지 함께 본다.
4. 관찰용 로그: 클라이언트 history와 서버 이력의 턴 수 차이만 `[CHAT-HISTORY-DIFF] client=… server=…`(내용 금지)로 1~2주 남긴 뒤 지운다.

대가:
- 세션 ID가 바뀌면(새 탭에서 새 세션) 이력이 비어 시작한다 - FE도 지금 같은 동작이다.
- 턴마다 DB 조회가 1회 는다(직전 1건 조회가 이미 3회 있다 - 한 번 읽어 나눠 쓰도록 합치면 오히려 줄어든다).
- 서버 기록이 저장에 실패한 턴은 이력에서 빠진다(지금은 FE 화면에 남아 있으면 보낸다).
- 기록 삭제 API(`DELETE /chat/logs`)를 부르면 그 세션의 맥락도 사라진다 - 의도와 맞다.

### B안 - 클라이언트 history를 서버 기록과 대조해 어긋나면 버린다
같은 턴 수·내용 해시가 맞을 때만 쓴다. 버튼 라벨 차이 때문에 대조 규칙이 복잡하고, 결국 서버 기록을 읽어야 하므로 A안보다 이득이 없다. 추천하지 않는다.

### C안 - BE가 history를 지운다
BE 중계가 `history`를 빈 배열로 보낸다. AI가 서버 이력을 만들지 않으면 맥락이 통째로 사라진다. A안을 먼저 넣은 뒤의 정리 단계로만 의미가 있다.

## 6. FE·BE 영향

- **FE**: 필수 변경 없음(보내는 `history`는 무시된다). 정리 단계에서 `history`를 빼면 요청 크기가 준다. 화면 표시용 대화 목록은 그대로다.
- **BE**: 필수 변경 없음. 정리 단계에서 `ChatRelayRequest.history`를 받지 않게 할 수 있다(그 전에 AI 배포가 먼저).
- **응답 필드**: 바뀌지 않는다.

## 7. 이행 순서

1. AI: 서버 이력 조립 함수 + 관찰 로그(`[CHAT-HISTORY-DIFF]`)만 넣고 **아직 클라이언트 history를 쓴다**. 1주 관찰로 차이(버튼 턴·저장 실패·세션 바뀜)를 본다.
2. AI: 서버 이력으로 전환. 안전 근거(H5·H6)는 서버 `selfHarm` 표시도 함께 본다. 시험지 v5 위기·예약 문항 재측정(라우터 입력이 바뀌므로 위기 문항 전부, `run_eval` 고정 시험 ID).
3. FE·BE: `history` 전송 제거(선택).

## 8. 정할 것

1. 서버 이력 턴 수 - FE와 같은 24(말풍선 기준)로 둘지, 라우터 8턴 기준 12개로 줄일지.
2. 위기 근거를 서버 `selfHarm` 표시로만 볼지, 자해 키워드 재검사도 함께 할지(추천: 둘 다).
3. 버튼 턴을 이력에 어떻게 넣을지 - 생략 / 선택값만(추천) / `[선택] …` 그대로.
4. 관찰 기간(추천 1주)과 전환 기준(차이 비율).
